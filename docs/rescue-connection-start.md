## 流れ

```text
ホスト（受付 ON）                gateway                         担当者（MCP client）
  その回だけの鍵 K を作る
  受付口へ WSS、K で proof ──────→ 受付の記録、接続コードを発行
  署名を検証してコードを出す ←── 受付の結果（gateway の鍵で署名）
  利用者がコードを担当者に伝える ·····························→ コードを含めて要求
                                  token 検証 → rescue_operator
                                  → 失敗の枠 → コード照合（消費）
                                  → 担当者のその回だけの鍵 C を作る
  身元の証明を検証 ←──────────── 身元の証明（gateway の鍵で署名）
  ポップアップ（ネイティブの補助、60 秒）
  許可: grant を発行、
  回答と dispatch を K で署名 ──→ 回答を検証、dispatch で Connect
  channel（SSH、host 鍵 = K、許可鍵 = C だけ）──────────────────→ route → initialize で束縛
```

受付の接続と channel は、同じ WSS の stream に載せます。
許可までは制御のやりとりに使い、許可の後は channel に切り替えます。
今の登録経路（`/tether-agent/v1/register`）が WSS の stream を channel に渡すのと同じ形です。

## 鍵と信頼の根

| 鍵 | 持ち主 | 寿命 | 用途 |
| --- | --- | --- | --- |
| ホストのその回だけの鍵 K（Ed25519） | ホスト。メモリのみで、ディスクに書かない | 受付 ON から、セッションの終わり（期限・ホスト側の切断・猶予の超過・拒否・時間切れ・コードの失効）まで | 受付の登録と再接続の proof、回答の署名、channel の host 鍵 |
| 担当者のその回だけの鍵 C（Ed25519） | gateway。メモリのみ | コードの照合の成功から、セッションの終わりまで。gateway の再起動でも消える | channel の公開鍵認証。身元の証明に入れ、許可鍵集合にする |
| 身元の証明鍵（Ed25519） | gateway の保護設定。公開鍵はホストのアプリに同梱して pin する | 鍵の差し替えはアプリの更新で行う。同梱は現行と次の 2 つまで | 受付の結果と身元の証明に署名する |

両端の鍵をどちらもセッションごとにします。#404 の「鍵はセッションごとに作り、終わったら捨てる。使い続けられるキーは持たない」を、ホスト側と担当者側の両方に当てます。
principal の今の signer（gateway の保護設定にある長期の鍵）は、レスキューでは使いません。常駐と、今の `Connect` の経路では今のまま使います。
ホストが信じる根は、アプリに同梱した身元の証明鍵の公開鍵だけです。
配布物の真正性（署名と notarization）に依存します。配布は未完です（[検証状態](tether-pilot-status.md)）。

## 1. ホストの指し方（受付と接続コード）

### 受付の登録

1. 利用者がレスキューのモードで受付を ON にすると、ホストは新しい K を作ります。
2. ホストは gateway の受付口（仮: `/tether-agent/v1/rescue`、WSS、固定 subprotocol）に接続し、32 byte のホストの nonce を送ります。Worker は今の登録経路と同じく、認証 header と cookie を拒んで中継します。
3. gateway は 32 byte の gateway の nonce を送ります。
4. ホストは K で proof を返します。署名対象は、[ペア登録](host-pairing.md#登録口) と同じ長さ付きの連結で、次の値です。
   1. `rescue-host.agentgateway.rescue-reception\u0000v1\u0000`
   2. 受付口の公開 URL（設定の MCP resource の origin から作る。要求の `Host` から作らない）
   3. K の SSH wire 形式
   4. gateway の nonce
   5. 目的（`new` か `resume`）
   6. `resume` のときだけ、受付 id
5. gateway は上限を確かめ、受付 id（128 bit 乱数）と接続コードを作ります。
6. gateway は受付の結果を身元の証明鍵で署名して返します。署名対象は、`rescue-host.agentgateway.rescue-reception-result\u0000v1\u0000`、gateway の公開 URL、ホストの nonce、K の SSH wire 形式、受付 id、接続コードです。
7. ホストは pin した公開鍵で受付の結果を検証し、ホストの nonce と K が自分のものであることを確かめてから、コードを画面に出します。

proof が示すのは「K を持っている」ことだけで、ホストの身元ではありません。
アカウントの無いホストの登録口なので、誰でも登録できます。守りは回数の制限と、要求の側の認証です。
受付の結果の署名で、relay が別の受付のコードに差し替えることを防ぎます。

#### 受付口の wire

受付口は `GET /tether-agent/v1/rescue` の WSS で、subprotocol は `rescue-agent-reception.v1` だけです。text JSON frame を使い、各 message は 2 KiB 以下、nonce と署名・鍵は登録経路と同じ base64url（padding なし）です。
ホストは `hello`（nonce）、gateway は `challenge`（nonce）、ホストは `proof`（purpose=`new`、K、署名。resume の場合は reception id も含む）、gateway は `reception`（id、12 桁コード、署名）を送ります。署名対象は `RescueTranscript` と `RescueResultTranscript` です。
受付上限は upgrade 前に busy の 503（`Retry-After: 1`）、rate の 429（`Retry-After: 60`）で返します。拒否は reception frame を返さず close code 1008 で接続を閉じます。
reception の後、gateway は担当者の要求が来たら `request`（身元の証明）を 1 つだけ送ります。ホストは `request` を受けた後に `answer` を 1 つだけ送ります。`request` の後に届いた frame は回答として扱い、受け取れない形（JSON でない、binary、dispatch の確認に通らない `allow`）なら検証に通らない回答として `failed` で受付を終えます。それ以外の frame・close は受付を終えます。
`allow` の後、同じ WSS は登録経路と同じく binary の channel の stream になります。

| frame | 向き | 欄 | 署名 |
| --- | --- | --- | --- |
| `request` | gateway → ホスト | `nonce`（32 byte）、`client`（C の SSH wire）、`display_name`、`organization`、`profile`（`mac_current_user`）、`signature` | 身元の証明鍵で `RescueRequestTranscript` |
| `answer` | ホスト → gateway | `answer`（`allow`・`deny`・`timeout`）、`signature`。`allow` のときだけ、登録の frame と同じ dispatch の欄（`generation`、`launch_id`、`epoch`、`policy_digest`、`key_set_digest`、`profile`、`deadline_unix_nano`、`host_key`） | K で `RescueAnswerTranscript`。digest は `RescueRequestTranscript` の SHA-256 |

transcript の byte の並びは `backend/internal/agentgateway/rescue_request.go` にあり、試験 `rescue_wire_test.go` が固定します。

### 接続コード

- 12 桁の 10 進数字です。gateway が `crypto/rand` から一様に作ります（棄却標本化で偏りを出さない）。有効なコードと重なったら作り直します。
- 画面では 4 桁ずつ 3 組に区切って出します。照合の前に空白とハイフン（全角のものと、日本語の IME がハイフンのキーで打つ長音の「ー」を含む）を除き、全角の数字を半角に直します。チェックディジットは入れません。推測の空間を減らさないためです。
- 有効時間は gateway の時計で 5 分です。照合に使われた時点で消費し、許可・拒否・時間切れのどれでも二度と使えません。
- gateway はコードを、起動ごとの乱数の秘密を鍵にした HMAC-SHA-256 の値で引きます。コードの平文を記録やログに残しません。
- コードが失効したら受付を終えます。ホストは新しいコードを自動では取りません。利用者がもう一度受付を ON にします。

使い終わったコードの値が、後で別の受付に偶然もう一度出ることは除きません。
古いコードを送って当たる確率は、でたらめな 12 桁で当たる確率と同じで、下の推測への耐性の計算に含まれます。

### 受付 OFF のホストへの要求

ホストが受付を OFF にするか、受付の接続が切れると、gateway はその受付記録とコードをすぐ消します（要求の前なら猶予はありません）。
要求の後、ポップアップの答えが出る前に受付の接続が切れたら、gateway は要求を失効させ、ホストは確認中を拒否として終えます。
受付 OFF、コードの失効、使用済み、存在しないコードは、担当者に同じ「コードが無効」で返します。どれかを区別して漏らしません。
ホストの側でも、受付 OFF の状態で要求が届いたら、ポップアップを出さずに拒否します（gateway と競合したときの二重の守り）。

### 回数の制限

| 項目 | 値 | 超えたとき | 理由 |
| --- | --- | --- | --- |
| コードが有効な受付（gateway 全体） | 100 | 503。新しい受付を作らない | 推測耐性の計算の前提（下の N） |
| 受付記録の総数（猶予中を含む） | 1,000 | 503 | メモリの上限 |
| 新しい受付の登録（gateway 全体） | 1 分に 30 件 | 429 | 枯渇の緩和 |
| 新しい受付の登録（送信元 IP ごと） | 1 分に 5 件 | edge で拒否 | gateway は送信元を確かめられないため、Cloudflare の rate limiting rule で行う |
| コードの照合の失敗（principal ごと） | 10 分に 5 回 | その principal は 10 分間要求できない | 推測耐性。ほかの principal には影響しない |

照合の前に、その principal の失敗 1 回分の枠を不可分に確保し、照合に成功したときだけ枠を戻します。
同時の要求（principal ごとに 4 件まで）でも、10 分の窓で 5 回を超えて試せません。
成功しても、それまでの失敗の記録は消しません。
`rescue_operator` を持たない principal の要求は、枠を取る前に拒否します。
失敗の記録は、principal の label と時刻だけを持ちます。コードは記録しません。

### 推測への耐性

- コードの空間は S = 10^12（約 2^40）です。
- 1 回の照合で当たる確率は、有効なコードの数 N を使って N/S 以下です。N ≤ 100 なので 10^-10 以下です。
- 照合できるのは、IdP で認証し `rescue_operator` を持つ principal だけです。gateway の principal は最大 4 人（[gateway の上限](agent-gateway.md#上限)）です。
- 失敗の上限から、試行は全体で 1 時間に 4 × 30 = 120 回以下です。1 年で約 1.05 × 10^6 回です。
- 失敗の記録はメモリにあり、gateway の再起動で消えます。再起動ごとに、principal あたり最大 5 回の試行が増えます。毎日 1 回再起動しても、1 年で 4 × 5 × 365 = 7,300 回の増加で、上の回数の 1% 未満です。
- gateway の再起動が 1 日 1 回以下の運用なら、1 年間で 1 回でも当たる確率は、約 1.06 × 10^6 × 10^-10 ≈ 1.1 × 10^-4 以下です。再起動がそれより多いときは、回数に応じて計算し直します。特定の受付 1 件（5 分）を狙うなら、4 人で 20 回、2 × 10^-11 以下です。
- 当たっても、ホストにはポップアップが出て、担当者の名前と組織が見えます。利用者は知らない担当者を拒否できます。

匿名の外部の攻撃者は、コードを試せません。照合の前に token と役割を確かめるためです。
この計算の前提は、有効なコードの上限 N（100）、principal の上限（4）、照合の失敗の上限（principal ごとに 10 分に 5 回）、gateway の再起動の頻度（1 日 1 回以下）です。
どれかを変えるときは、先にこの計算をやり直します。
値は gateway の `backend/internal/agentgateway/rescue_code.go` と `MaxPrincipals` にあり、どちらのコードの注記もこの節を指します。

## 2. 身元の渡し方（身元の証明）

gateway は、コードの照合に成功した要求ごとに、担当者のその回だけの鍵 C を作ります。
そして身元の証明を作り、受付の接続でホストへ送ります。署名対象は、長さ付きの連結で次の値です。

1. `rescue-host.agentgateway.rescue-request\u0000v1\u0000`
2. gateway の公開 URL
3. 受付 id
4. 宛先のホストの K（SSH wire 形式）
5. 要求の nonce（gateway の 32 byte 乱数）
6. C の公開鍵（SSH wire 形式）
7. 担当者の表示名
8. 組織名
9. 操作範囲の識別子（固定の profile 名）

ホストは、pin した公開鍵で署名を検証し、受付 id と K が自分のものであること、この受付で最初の要求であることを確かめてから、ポップアップを出します。
どれかが合わなければ、ポップアップを出さずに拒否します。

### 名前と組織の出どころ

名前は gateway の設定の principal ごとの表示名から出します。
IdP の token の `name` などの claim は使いません。
今の gateway は検証した `sub` だけを識別に使い、`email` も存在の確認だけです（[認証と認可](agent-gateway.md#認証と認可分離)）。
IdP によっては、利用者が自分の表示名を変えられます。
token の `sub` は IdP の多要素認証で確かめた値で、運用者がその `sub` に表示名を登録します。
こうして、表示名は IdP で確かめた本人に結びつきます。
#404 の「IdP で確かめた名前と組織」は、「IdP で確かめた本人（`sub`）に、運用者が gateway の設定で登録した名前と組織」と読みます（[#404 の文言の読み替え](https://github.com/O2-CONNECTIVE/Tether/issues/404#issuecomment-6996862703)、2026-11-19、利用者の裁定）。

組織名は gateway 全体で 1 つの設定値で、gateway を運用する組織（確認する側）を表します。担当者ごとには確かめません。
gateway の principal は、同じ組織の最大 4 人です。

設定に足す member は、principal の `display_name`（1〜64 文字、制御文字と双方向制御文字を拒否）と、top-level の `organization`（同じ規則）です。
レスキュー用の host に載る principal は `display_name` を必須にします。

### 今の鍵の指紋との対応

今のパイロットでは、承認画面に principal の長期の signer の指紋を出し、受け手が承認した鍵で担当者が接続します。
この流れでは、長期の signer の代わりに、身元の証明に入れた C を使います。
許可したら、C だけを許可鍵集合にします。channel の handshake は、今と同じく LaunchID を user にした公開鍵認証で、C だけを通します（[認証と照合](agent-channel.md#認証と照合)）。
そのため、ポップアップに出した名前と、実際に接続してくる鍵が結びつきます。
C の指紋は、ポップアップの補足に短く出します。

### relay に対して守れることと守れないこと

relay（Cloudflare の Worker と Access の edge）は、受付の結果、身元の証明、回答を書き換えられません。どれも署名で守ります。
一方、relay が侵害されると、relay は中継した担当者の token（Access の assertion、OAuth の Bearer）を期限内にもう一度使い、担当者として要求し、許可の後の route も使えます。
そのとき、ポップアップには本物の担当者の名前が出ます。
これは今の MCP の経路と同じ境界で（[信頼の前提](agent-gateway.md#信頼の前提)）、この設計では防げません。送信者に結びついた token は範囲外です。
gateway が侵害された場合も守れません。gateway は身元の証明鍵と C を持つ信頼境界です。

## 3. 許可と拒否

### ポップアップ

- 主な表示: 「{組織} が確認: {表示名}」。例:「O2 CONNECTIVE が確認: 山田（サポート）」
- 内容: 操作範囲と期限（許可した時刻から選んだ期限まで。時刻で出す）
- 補足: C の指紋
- ボタン: 「拒否」と「許可」。既定のボタンは置きません。Return では何も起きず、Esc は拒否です。
- 表示から 1 秒間は「許可」を押せなくします。別の操作のクリックが、出た直後のポップアップに当たるのを防ぐためです。

### ポップアップを出す場所と判定

ポップアップは WebView に置かず、OS のネイティブの補助で出します。
#404 で、Mac に固有の同意の処理を Tauri の外のネイティブの補助に分けると決まっています。
UI の侵害や細工した IPC 入力を、認可の根拠にしないためです（[脅威モデル](threat-model.md#信頼境界と攻撃者)の UI の境界）。

判定は、ホスト側の Go の許可の状態機械が持ちます。
状態機械は、要求 id と表示する内容をネイティブの補助に渡し、補助から「要求 id・表示した内容の digest・許可か拒否」を受けます。
状態機械は、回答が補助の経路から来たこと、要求 id と digest が今の要求と一致すること、60 秒の内であることを確かめてから grant を発行します。
WebView から来た許可は受けません。
補助と Go の間の経路の認証と、Windows での補助の形は、#410 で決めます。
同じユーザーの権限を持つマルウェアが補助を操作する場合は守れません。今の `/dev/tty` の同意と同じ範囲です。

### 60 秒の自動拒否

- ホストの状態機械が、ポップアップを出した時点から、単調時計と壁時計の両方で数えます。どちらかが 60 秒を超えたら拒否です。壁時計が戻ったときも拒否です。
- 補助の画面のタイマーは表示だけです。60 秒を過ぎて届いた「許可」は捨てます。
- gateway は要求から 75 秒（60 秒と通信の余裕 15 秒）で要求を失効させます。その後に届いた許可の回答では channel を開かず、ホストに失効を伝えます。
- 許可の回答が gateway に届かなかったときは、ホストの grant は channel の handshake の期限で失効します（今の fail closed のとおり）。

### 回答

ホストは回答を K で署名して返します。
署名対象は、`rescue-host.agentgateway.rescue-answer\u0000v1\u0000`、受付 id、要求の nonce、身元の証明の digest、回答（`allow`・`deny`・`timeout`）です。
`allow` のときは、grant の dispatch（Binding と期限）も署名対象に入れます。gateway はこれを検証して、C を signer にして `Connect` します。
host 鍵は、設定の host の鍵（今の `Connect` の照合）ではなく、受付記録の K に pin します。
dispatch を真正に届ける責任は登録 adapter にあり（[信頼の前提](agent-gateway.md#信頼の前提)）、この回答の署名がそれを担います。

担当者には、`allow`・`deny`（拒否）・`timeout`（時間切れ）を区別して返します。コードが正しかった場合だけなので、区別しても推測の手がかりになりません。
拒否と時間切れの後、ホストは K を、gateway は C を捨てて受付を終えます。次は利用者がもう一度受付を ON にします。

### 担当者の入口

担当者は MCP の新しい tool で、コードを含めて要求します。
tool は非同期の 2 つです（#423 で決定）。Worker が MCP の 1 往復を 35 秒で切るため、75 秒まで待つ同期の tool は本番の経路で通りません。

- `rescue_request`（引数は `code` だけ）: 照合して身元の証明をホストへ送ったら、すぐ `pending` を返します。拒否（コードが無効、失敗の枠、確認中・セッション中の要求がある、`rescue_operator` が無い、表示名か組織の設定が無い）は tool のエラーで返します。コードが無効の文言は、受付 OFF・失効・使用済み・存在しないで同じです。
- `rescue_request_status`（引数なし）: 今の要求の状態（`none`・`pending`・`allow`・`deny`・`timeout`・`ended`・`failed`）を返します。`pending` の間は、呼び出しの時間の上限まで変化を待ちます。`ended` は回答の前に受付が終わったこと、`failed` は回答を検証できない・接続できないことです。

2 つの tool は、route に束縛していない session（discovery session）にだけ出します。
今の MCP は、tool の引数で host や signer を指定させません（[呼出し経路](agent-gateway.md#呼出し経路)）。
この tool は route を選ぶものではなく、ホストに許可を求めるだけです。route は、ホストが許可した後に gateway が作ります。
session を後から grant に束縛しない今の規則は変えません。許可の後、担当者の client は新しい `initialize` で route に束縛します。

1 人の principal が持てる、確認中・セッション中・猶予中の受付は 1 つです（live route は 1 principal に 1 本という今の規則と同じ）。
その間の新しい要求は拒否します。

## 4. セッションの鍵と猶予

### ホストの状態

| 状態 | 入る条件 | 出る条件 |
| --- | --- | --- |
| 受付中 | 受付 ON。K を作り、コードを出す | 要求が届く → 確認中。コードの失効・受付 OFF → 終了 |
| 確認中 | 身元の証明を検証してポップアップ | 許可 → セッション中。拒否・時間切れ・受付の接続の切断 → 終了 |
| セッション中 | grant を発行し、channel が開く | 切断 → 猶予中。期限・ホスト側の切断 → 終了 |
| 猶予中 | channel が切れた | 同じ K と同じ C で再接続 → セッション中。猶予の超過 → 終了して受付を自動で再開（期限の前で、清掃を確認できたときだけ）。期限・ホスト側の切断・回収の未確認 → 終了 |
| 終了 | 上のどれか | なし。K を捨て、停止と回収に進む |

ホスト側の切断は、利用者の停止の操作、受付 OFF、アプリの終了、OS のログアウトや再起動です。
K はメモリだけにあるので、アプリが終われば K も消えます。
スリープはホスト側の切断ではなく、猶予の時間として数えます。

### 猶予の値

5 分にします。設定では変えません。

- 切断の検出に最大で約 30 秒かかります（心拍 10 秒・応答待ち 10 秒、読取りの停滞 30 秒。[gateway の上限](agent-gateway.md#上限)の channel の予算）。
- Wi-Fi の切り替え、VPN の張り直し、テザリングへの切り替えは、数秒から 1 分ほどです。再接続の間隔を 1・2・4・8・16・30 秒と延ばしても、5 分あれば十分に戻れます。
- 長くするほど、K や C が漏れたときに許可なしで接続できる時間が延びます。#404 の追加の裁定の理由は、この時間を短くすることです。
- 接続コードの有効時間と同じ 5 分なので、利用者に説明しやすくなります。

### 猶予の数え方

- **ホストの時計で数えます。** 許可と K を持つのはホストです。gateway が侵害されても、ホストは猶予を過ぎた再接続を拒めます。
- 起点は、相手から最後に正しい frame（心拍の応答を含む）を受けた時点です。切断を検出した時点ではありません。検出の遅れの分だけ猶予が延びるのを防ぎます。
- 期限と同じく、単調時計と壁時計の両方で数え、どちらかが 5 分を超えたら超過です（[agent channel](agent-channel.md) の `WallRecheck` と経過予算と同じ流儀）。壁時計が起点より前に戻ったときも超過として扱います。
- スリープの間は、単調時計が止まることがあります（macOS）。壁時計はスリープ中も進むので、復帰後 1 秒以内に壁時計で超過を見つけます。5 分を超えるスリープの後は、セッションを終えます。セッション中のスリープは [#400](https://github.com/O2-CONNECTIVE/Tether/issues/400) で防ぎます。
- gateway も、自分が相手から最後に正しい frame を受けた時点から 5 分（gateway の単調時計）で、受付記録と C を捨て、以後の `resume` を拒否します。余裕は置きません。ホストが猶予を終えた後に、gateway が旧い C で接続できる時間を残さないためです。両者の起点はほぼ同じで、gateway が先に切っても、境界の正規の再接続が失敗するだけです（安全側）。猶予を過ぎた再接続をホストが拒むのは変わりません。

### 猶予の間の再接続の確かめ方

猶予の間に再接続できるのは、同じ担当者の、同じセッションの鍵だけです。次の 4 つをすべて確かめます。

1. **ホストから gateway（同じ K）:** ホストは受付口に `resume` で接続し、K で proof を返します。署名対象に受付 id を入れます。gateway は受付記録の K の公開鍵で検証します。K を持たない者は、この受付を名乗れません。
2. **gateway の route（同じ担当者）:** gateway は、受付記録に固定した principal（label と subject）と C でだけ `Connect` します。route を使えるのは、その principal の token で作った MCP session だけです（今の session の束縛）。
3. **channel の handshake（同じ鍵の組）:** ホストは、許可したときの C だけで公開鍵認証を通します。gateway は host 鍵を K に pin します。commitment に接続世代を入れ、ホストは次の世代以外を拒否します。
4. **ホストの状態:** 猶予中であること（両方の時計）、前の接続の作業の回収を確認済みであること、受付 OFF でないこと。

同じ組織の別の担当者は、2 で gateway が、3 でホストが拒否します。C は受付ごとに作るので、別の受付の C でも通りません。
K を盗んだ者は、C を持たないので担当者として接続できません。
猶予の間の再接続では、ポップアップを出しません。画面に「再接続しました」と出します。

### 接続世代

猶予の間は grant を失効させず、新しい作業の受け付け（admission）だけを止めます。
猶予に入るのは、確立した channel の通信の切断（transport の終了、心拍の失敗、読み書きの停滞）だけです。取消、書込み失敗、正規 stop、期限、相手の違反、Accept 前の認証失敗は、今のとおりすぐ失効させます。
再接続は、同じ grant の新しい接続世代（1 から増やす）として開きます。

- channel の commitment に世代を入れます。gateway は (LaunchID, 世代) の組を 1 回だけ使います。ホストの Session は、世代ごとに transport を 1 回だけ受け取ります。
- 期限、許可鍵集合、操作範囲、境界は、世代が変わっても変えません。期限は延びません。
- 接続世代は、今の `Binding.Generation` や常駐の世代とは別の値です。名前と wire で区別します。
- 今の「1 grant に接続 1 回」（[agent channel](agent-channel.md)）を、「1 grant に、世代ごとに接続 1 回」に改めます。実装は [#425](https://github.com/O2-CONNECTIVE/Tether/issues/425) です。

### 猶予の間の作業

切断したら、実行中の作業は今と同じく取り消して回収します。
切断の後も作業を続ける契約の変更は別の issue にする、と #399 で決まっているためです（[PR #413](https://github.com/O2-CONNECTIVE/Tether/pull/413) の「1コマンドのtimeoutの上限240秒は据え置きます」）。
回収を確認できなければ、猶予の間の再接続も拒否し、要清掃のまま終えます（[停止・削除・記録完了は別の結果](temporary-guest-account.md#停止削除記録完了は別の結果)）。
再接続の後は、新しい作業を始められます。

### 猶予の超過

1. 猶予を超えたら、ホストは grant を失効させ、K を捨てて、ゲストの回収に進みます。gateway も 5 分で受付記録と C を捨てます。
2. ホストは受付を自動で再開します。新しい K' を作り、新しい受付として登録し、新しいコードを出します。オフラインのままなら、戻れたときに登録します。
   再開するのは、許可の期限に達しておらず、ホスト側の切断でもなく、旧いセッションの回収と清掃を確認できたときだけです。
   期限とホスト側の切断は、猶予の超過より優先します。スリープの後などに両方を同時に見つけたら、期限として扱い、オフラインの間に予約した再登録も取り消します。
   清掃を確認できなければ、要清掃のまま受付を再開しません（[停止・削除・記録完了は別の結果](temporary-guest-account.md#停止削除記録完了は別の結果)）。
3. 利用者が新しいコードを担当者に伝え、担当者が要求すると、ホストに許可のポップアップがもう一度出ます。60 秒の自動拒否も同じです。
4. 許可したら、新しい grant を発行します。期限は、その許可の時刻から選んだ期限までです。ゲストのアカウントも新しく作ります。

これで「猶予を過ぎたら、ホストに許可のポップアップを出し直す」を満たします。
コードを伝え直さずに同じ担当者だけがポップアップを出せる形も考えましたが、採りません（2026-11-19、利用者の裁定で確定）。
アカウントの無いホストが「同じホストに戻った」ことを gateway に示すには、猶予の後も効く秘密（旧い K による引き継ぎなど）が要ります。
その秘密が漏れると、漏れた鍵の効力が猶予の後まで延び、ホストがオフラインの間に受付を別の端末へ移せてしまいます。
鍵の漏れの効力を猶予の間に限るという追加の裁定の理由を優先しました。

### 期限とホスト側の切断

猶予に関わらず、grant を失効させ、K を捨て、停止と回収に進みます。受付は自動では再開しません。
ホストは gateway に接続していれば受付の終了を伝え、gateway は C を捨てます。
接続していなければ、gateway は 5 分で受付記録と C を捨てます。

### 中継の寿命

受付の接続と channel は同じ WSS に載るため（[流れ](#流れ)）、Worker の中継は受付からセッションの終わりまでを 1 本で運びます。
Worker はレスキューの受付口（subprotocol `rescue-agent-reception.v1`）の中継にだけ、登録と resident の 5 分とは別の絶対の寿命を置きます。

寿命は 24 時間 10 分です。
根拠となる時間は、受付の handshake 10 秒（agenttransport の登録予算 `DefaultBudgets().Registration`）+ コードの有効時間 5 分 + gateway の要求の失効 75 秒 + 許可の期限の上限 24 時間 = 24 時間 6 分 25 秒です。
これに時計の進み方の違いと、期限で閉じるやりとりの余裕を足しています。

frame の予算は登録と同じ率（5 分に 4096 frame）で、1,187,840 frame です。
channel の心拍は両端が 10 秒ごとに送り、相手のものに答えます。
これを寿命の間流しても各方向 17,400 frame で、予算の 2% に届きません。

期限は今までどおりホストと gateway が判定します（[#399](https://github.com/O2-CONNECTIVE/Tether/issues/399)）。
受付中は、要求の無いままコードが失効したら gateway が受付の接続を閉じ、確認中は要求の失効で終わります。
中継の寿命はこれらの外側の上限で、期限の上限より後に来るように選んでいます。
寿命に達したら Worker は両端を close code 4000 で閉じ、再接続も延長もしません。

Cloudflare 側の都合で、寿命より前に切れることがあります。
runtime の更新では、旧い process の接続は最大 20 分の猶予の後に切れます（[runtime updates](https://developers.cloudflare.com/workers/platform/limits/#runtime-updates)）。
障害や資源の逼迫では、もっと早く切れることがあります。
channel が開いた後に切れたら、channel の切断なので、猶予の間に再接続します。
再接続は新しい WSS であり、新しい中継の寿命で始まりますが、期限は延びません。
受付中や確認中に切れたら猶予はなく、受付の接続の切断として扱います（[受付 OFF のホストへの要求](#受付-off-のホストへの要求)）。

期限の上限、コードの有効時間、要求の失効のどれかを変えるときは、この寿命も見直します。
値は `deploy/cloudflare/native/worker.mjs` の `RESCUE_LIMITS` にあります。

### ゲストのアカウントとの対応

| 事象 | grant | 鍵 | ゲストのアカウント | 作業 |
| --- | --- | --- | --- | --- |
| 許可 | 発行 | K と C を保持 | 作成（[作成と有効化の境界](temporary-guest-account.md#作成と有効化の境界)） | 受け付ける |
| 切断（猶予に入る） | 失効させない。admission を止める | K と C を保持 | 所有の記録を保持し、削除しない。状態は ADR 0003 のとおり（token の取得の後は無効） | 取り消して回収 |
| 猶予の間の再接続 | 同じ grant の次の世代 | 同じ K と C | 同じアカウント。新しい作業は ADR 0003 の有効化・token の取得・再無効化の手順を通す | 受け付ける |
| 猶予の超過・期限・ホスト側の切断・拒否 | 失効 | 捨てる | 停止の手順で無効化・回収・削除 | 回収 |

猶予の間も、アカウントを有効のまま待たせません。
[ADR 0003](adr/0003-owned-guest-workload.md) では、local BATCH logon の token を取ったらアカウントを再び無効化します。猶予はこの手順を変えません。

今の Mac の入口は、現在ユーザーの権限で隔離なしに動きます（[Mac runtime](mac-agent-runtime.md)）。
[一時guestアカウント](temporary-guest-account.md) の設計は Windows の API で書かれていて、Mac のゲストのアカウントは未設計です。
この流れを製品として有効にするのは、そのホストの OS でゲストのアカウントを使えるようになってからです。
それまでは、Go の側の受付・コード・身元の証明・許可の状態機械を、今の境界（現在ユーザー・隔離なし）で試験だけに使います。ポップアップには、今の承認画面と同じく隔離なしの警告を出します。

| 許可鍵集合は設定の Client 鍵（principal の長期の signer） | 許可鍵集合はその回だけの C 1 つ |
| 期限は設定の絶対時刻（上限 24 時間） | 期限は許可の時刻から、選んだ 2・4・8・12・24 時間（既定 2 時間） |
| 1 grant に接続 1 回、再接続なし | 猶予 5 分の間だけ、同じ grant の次の世代で再接続 |

確認文字列が守っていたのは、本人がその場で画面を見て同意したことと、引数や pipe で同意を渡せないことです。
この流れでは、ネイティブの補助で出すこと、既定ボタンを置かないこと、表示直後の無効化、60 秒の自動拒否、画面の値を認可の根拠にしない状態機械で守ります。

今の経路（`rescue-mac-agent -config`、確認文字列、旧の `Connect`）は残します（[#424](https://github.com/O2-CONNECTIVE/Tether/issues/424) で決定）。
#424 で許可の状態機械は入りましたが、Mac のゲストのアカウントが未設計なので、この流れは製品として有効にせず、試験だけで使います。製品として有効にできるまで、今の Mac の入口は今の経路だけです。
この流れを製品として有効にする issue で、レスキューの入口をこの流れに切り替え、今の承認画面と確認文字列をレスキューから外します。
[検証状態](tether-pilot-status.md)の固定証跡は履歴として残し、この流れの成功に読み替えません。

## 試験で確かめること

#409 の受け入れ条件と、追加の裁定の分です。実装の issue で red から書きます。
実装は、依存の順に [#421](https://github.com/O2-CONNECTIVE/Tether/issues/421)（接続コード）→ [#422](https://github.com/O2-CONNECTIVE/Tether/issues/422)（受付口）→ [#423](https://github.com/O2-CONNECTIVE/Tether/issues/423)（担当者の要求と身元の証明）→ [#424](https://github.com/O2-CONNECTIVE/Tether/issues/424)（ホストの許可の状態機械）→ [#425](https://github.com/O2-CONNECTIVE/Tether/issues/425)（猶予と接続世代）に分けました。

| 確かめること | 試験の形 |
| --- | --- |
| 受付 OFF のホストに要求が届かない | 受付 OFF の後のコードの照合が「コードが無効」になり、ホストに要求が届かない。ホストは受付 OFF のときに届いた要求でポップアップを出さない |
| コードは 1 回だけで、失効後は使えない | 2 回目の照合が無効。5 分を過ぎたコードが無効。拒否・時間切れの後のコードが無効 |
| `rescue_operator` の無い principal は要求できない | `resident_owner` だけの principal の要求が、コードの照合の前に拒否される（失敗の枠も取らない） |
| 拒否と 60 秒の自動拒否で接続が始まらない | 拒否・時間切れで grant が発行されず、`Connect` が呼ばれない。60 秒を過ぎた許可の回答を捨てる。75 秒を過ぎた回答で gateway が channel を開かない。WebView の経路から来た許可を受けない |
| 期限と切断で鍵が捨てられ、同じ鍵で再接続できない | 期限・ホスト側の切断・猶予の超過の後、K での `resume`、C での channel、旧 grant の Binding での channel が拒否される |
| 猶予の間は同じ担当者・同じ鍵で再接続できる | 5 分以内の `resume` で次の世代の channel が開く。別の principal・別の C・同じ世代の再利用は拒否される |
| 猶予の数え方 | 単調時計だけが進む場合・壁時計だけが進む場合（スリープの模擬）・壁時計が戻る場合のそれぞれで、5 分を超えたらセッションを終える |
| 猶予の超過の後 | 受付が新しい K' とコードで再開し、新しいコードの要求でだけポップアップが出る。期限と猶予の超過を同時に見つけたとき、清掃を確認できないときは、受付を再開しない。gateway は最後の frame から 5 分を過ぎた `resume` を拒否する |
| 回数の制限 | 失敗 5 回で principal が 10 分止まり、ほかの principal は止まらない。同時 4 件の要求でも 10 分に 5 回を超えない。有効なコードが 100 件で新しい受付が 503 になる |
| 署名 | 受付の結果・身元の証明のどれかの値が違えば、ホストはコードを出さない・ポップアップを出さない。表示名と組織が設定から来る |

## 脅威と残るリスク

| 脅威 | 守り | 残るもの |
| --- | --- | --- |
| コードの推測 | 12 桁、5 分、1 回限り、照合は `rescue_operator` だけ、principal ごとの失敗の上限 | 1 年で 1.1 × 10^-4 以下の確率。当たってもポップアップで拒否できる |
| 匿名の受付で枠を埋める | 有効なコードの上限、全体と IP ごとの登録の速度 | 多数の IP からの攻撃では、正規の利用者が受付を ON にできないことがある（可用性） |
| 利用者からコードを聞き出す | 照合できるのは `rescue_operator` だけ。ポップアップに名前と組織が出る | 内部の担当者による悪用。監査の記録で追う |
| 偽のホストのコードを担当者に渡す | 担当者がコードを利用者本人から受け取る運用 | 担当者が偽のホストに作業を送ること。担当者の側の情報が漏れうる |
| relay が受付の結果・身元の証明・回答を書き換える | 身元の証明鍵と K の署名、channel の鍵の pin | なし |
| relay が担当者の token をもう一度使う | なし（今の MCP の経路と同じ境界） | relay が侵害されると、本物の担当者の名前で要求し、許可の後の route を使える。送信者に結びついた token は範囲外 |
| K や C の漏れ | どちらもメモリのみで、セッションごと。猶予の超過・期限・終了で捨てる | 漏れた鍵の効力はセッションの終わりまで（猶予の間を含む） |
| ポップアップの誤操作 | 既定ボタンなし、1 秒の無効化、60 秒 | 利用者が読まずに許可すること |
| UI の侵害 | 許可の操作は WebView で受けず、ネイティブの補助だけ | 同じユーザーの権限のマルウェア（範囲外） |
| ポップアップの連発 | コードは 1 回限りで、1 コードにポップアップ 1 回 | なし |
| gateway の侵害 | 範囲外。身元の証明鍵と C を持つ信頼境界 | 身元の偽装と接続 |
| gateway の再起動 | 状態はメモリのみ。受付記録と C が消え、ホストの `resume` は失敗し、猶予は終わる | 再起動の直後の再接続ができない（安全側）。失敗の記録が消える分は推測への耐性に含めた |

## 範囲外と後続

- ポップアップと受付の画面、ネイティブの補助と Go の間の経路（[#410](https://github.com/O2-CONNECTIVE/Tether/issues/410)）。
- Mac のゲストのアカウントの実体（作成・削除・権限の確認）。Windows は [ADR 0003](adr/0003-owned-guest-workload.md) と [一時guestアカウント](temporary-guest-account.md) の経路です。
- 猶予の間も作業を続けること。#399 で別の issue にすると決まっています。
- 担当者の交代と、1 人の担当者が同時に複数のホストを助けること。
- 担当者の多要素認証の強制（[#398](https://github.com/O2-CONNECTIVE/Tether/issues/398)）。#415 の `role_assurance` の `multi_factor` は #398 が入るまで指定できません。製品として有効にする前提です。
- 送信者に結びついた token（relay の侵害で担当者の token をもう一度使われることへの対策）。
- 身元の証明鍵の配布と差し替えの手順（配布の issue）。
