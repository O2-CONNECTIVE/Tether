## 前提にした決定

- [#404](https://github.com/O2-CONNECTIVE/Tether/issues/404) の確定（2026-11-18）: ホスト側はアカウントを持たない。受付 ON の間だけ要求を受ける。要求の時点で許可のポップアップを出し、IdP で確かめた担当者の名前と組織を主に出す。「許可」を既定のボタンにしない。60 秒で自動拒否する。鍵はセッションごとに作り、終わったら捨てる。
- #404 の追加の裁定（2026-11-19）: 切断から短い猶予（目安 5 分）の間だけ、許可をやり直さずに再接続する。猶予を過ぎたら許可のポップアップを出し直す。期限とホスト側の切断では、猶予に関わらず鍵を捨てる。
- [#399](https://github.com/O2-CONNECTIVE/Tether/issues/399): 許可の期限は 2・4・8・12・24 時間から選び、既定は 2 時間。経過時間と壁時計の両方で判定し、スリープ中も進める。期限が来たら停止と回収に進む。
- [#408](https://github.com/O2-CONNECTIVE/Tether/issues/408)（[PR #415](https://github.com/O2-CONNECTIVE/Tether/pull/415)、未 merge）: principal の役割 `rescue_operator` と `resident_owner`。レスキューの要求には `rescue_operator` を求める。gateway 内の判定口は principal の `rescue` です。
- 決定を docs に書く [PR #413](https://github.com/O2-CONNECTIVE/Tether/pull/413) も未 merge です。この文書は #413 の「決まったレスキューの始め方」の未定の点に答えます。

## 流れ

```text
ホスト（受付 ON）                gateway                         担当者（MCP client）
  その回だけの鍵 K を作る
  受付口へ WSS、K で proof ──────→ 受付の記録、接続コードを発行
  コードを画面に出す ←───────────
  利用者がコードを担当者に伝える ·····························→ コードを含めて要求
                                  token 検証 → rescue_operator
                                  → 失敗回数 → コード照合（消費）
  身元の証明を検証 ←──────────── 身元の証明（gateway の鍵で署名）
  ポップアップ（60 秒）
  許可: grant を発行、
  回答と dispatch を K で署名 ──→ 回答を検証、dispatch で Connect
  channel（SSH、host 鍵 = K、許可鍵 = 担当者の signer 1 つ）────→ route → initialize で束縛
```

受付の接続と channel は、同じ WSS の stream に載せます。
許可までは制御のやりとりに使い、許可の後は channel に切り替えます。
今の登録経路（`/tether-agent/v1/register`）が WSS の stream を channel に渡すのと同じ形です。

## 鍵と信頼の根

| 鍵 | 持ち主 | 寿命 | 用途 |
| --- | --- | --- | --- |
| その回だけの鍵 K（Ed25519） | ホスト。メモリのみで、ディスクに書かない | 受付 ON から、期限・ホスト側の切断・猶予の超過・拒否まで | 受付の登録と再接続の proof、回答の署名、channel の host 鍵 |
| 担当者の signer（Ed25519） | gateway の保護設定（今の principal の signer） | 今のまま | channel の公開鍵認証。身元の証明に入れ、許可鍵集合にする |
| 身元の証明鍵（Ed25519） | gateway の保護設定。公開鍵はホストのアプリに同梱して pin する | 鍵の差し替えはアプリの更新で行う。同梱は現行と次の 2 つまで | 担当者の名前・組織・signer を、受付と K に結んで署名する |

ホストが信じる根は、アプリに同梱した身元の証明鍵の公開鍵だけです。
配布物の真正性（署名と notarization）に依存します。配布は未完です（[検証状態](tether-pilot-status.md)）。
使い続けられるホストの鍵は持ちません。#404 の決定のとおりです。

## 1. ホストの指し方（受付と接続コード）

### 受付の登録

1. 利用者がレスキューのモードで受付を ON にすると、ホストは新しい K を作ります。
2. ホストは gateway の受付口（仮: `/tether-agent/v1/rescue`、WSS、固定 subprotocol）に接続します。Worker は今の登録経路と同じく、認証 header と cookie を拒んで中継します。
3. gateway は 32 byte の nonce を送ります。
4. ホストは K で proof を返します。署名対象は、[ペア登録](host-pairing.md#登録口) と同じ長さ付きの連結で、次の値です。
   1. `rescue-host.agentgateway.rescue-reception\u0000v1\u0000`
   2. 受付口の公開 URL（設定の MCP resource の origin から作る。要求の `Host` から作らない）
   3. K の SSH wire 形式
   4. gateway の nonce
   5. 目的（`new`・`resume`・`rekey` のどれか）
5. gateway は上限を確かめ、受付 id（128 bit 乱数）と接続コードを作り、コードと残り時間を返します。

proof が示すのは「K を持っている」ことだけで、ホストの身元ではありません。
アカウントの無いホストの登録口なので、誰でも登録できます。守りは回数の制限と、要求の側の認証です。

### 接続コード

- 12 桁の 10 進数字です。gateway が `crypto/rand` から一様に作ります（棄却標本化で偏りを出さない）。有効なコードと重なったら作り直します。
- 画面では 4 桁ずつ 3 組に区切って出します。照合の前に空白とハイフンを除きます。チェックディジットは入れません。推測の空間を減らさないためです。
- 有効時間は gateway の時計で 5 分です。照合に使われた時点で消費し、許可・拒否・時間切れのどれでも二度と使えません。
- gateway はコードを、gateway の秘密を鍵にした HMAC-SHA-256 の値で引きます。コードの平文を記録やログに残しません。
- コードが失効しても受付記録を消すだけで、ホストは新しいコードを自動では取りません。利用者がもう一度受付を ON にします。

### 受付 OFF のホストへの要求

ホストが受付を OFF にするか、受付の接続が切れると、gateway はその受付記録とコードをすぐ消します（要求の前なら猶予はありません）。
受付 OFF、コードの失効、使用済み、存在しないコードは、担当者に同じ「コードが無効」で返します。どれかを区別して漏らしません。
ホストの側でも、受付 OFF の状態で要求が届いたら、ポップアップを出さずに拒否します（gateway と競合したときの二重の守り）。

### 回数の制限

| 項目 | 値 | 超えたとき | 理由 |
| --- | --- | --- | --- |
| コードが有効な受付（gateway 全体） | 100 | 503。新しい受付を作らない | 推測耐性の計算の前提（下の N） |
| 受付記録の総数（猶予と再許可待ちを含む） | 1,000 | 503 | メモリの上限 |
| 新しい受付の登録（gateway 全体） | 1 分に 30 件 | 429 | 枯渇の緩和 |
| 新しい受付の登録（送信元 IP ごと） | 1 分に 5 件 | edge で拒否 | gateway は送信元を確かめられないため、Cloudflare の rate limiting rule で行う |
| コードの照合の失敗（principal ごと） | 10 分に 5 回 | その principal は 10 分間要求できない | 推測耐性。ほかの principal には影響しない |

失敗の記録は、principal の label と時刻だけを持ちます。コードは記録しません。

### 推測への耐性

- コードの空間は S = 10^12（約 2^40）です。
- 1 回の照合で当たる確率は、有効なコードの数 N を使って N/S 以下です。N ≤ 100 なので 10^-10 以下です。
- 照合できるのは、IdP で認証し `rescue_operator` を持つ principal だけです。gateway の principal は最大 4 人（[gateway の上限](agent-gateway.md#上限)）です。
- 失敗の上限から、試行は全体で 1 時間に 4 × 30 = 120 回以下です。1 年で約 1.05 × 10^6 回です。
- 1 年間で 1 回でも当たる確率は、1.05 × 10^6 × 10^-10 ≈ 1.1 × 10^-4 以下です。特定の受付 1 件（5 分）を狙うなら、4 人で 20 回、2 × 10^-11 以下です。
- 当たっても、ホストにはポップアップが出て、担当者の名前と組織が見えます。利用者は知らない担当者を拒否できます。

匿名の外部の攻撃者は、コードを試せません。照合の前に token と役割を確かめるためです。
principal の上限（4）を上げるときは、この計算をやり直します。

## 2. 身元の渡し方（身元の証明）

gateway は、コードの照合に成功した要求ごとに、身元の証明を作って受付の接続でホストへ送ります。
署名対象は、長さ付きの連結で次の値です。

1. `rescue-host.agentgateway.rescue-request\u0000v1\u0000`
2. gateway の公開 URL
3. 受付 id
4. 宛先のホストの K（SSH wire 形式）
5. 要求の nonce（gateway の 32 byte 乱数）
6. 要求の種類（`new` か `reapproval`）
7. 担当者の signer の公開鍵（SSH wire 形式）
8. 担当者の表示名
9. 組織名
10. 操作範囲の識別子（固定の profile 名）

ホストは、pin した公開鍵で署名を検証し、受付 id と K が自分のものであること、この受付で最初の要求であることを確かめてから、ポップアップを出します。
どれかが合わなければ、ポップアップを出さずに拒否します。

### 名前と組織の出どころ

名前は gateway の設定の principal ごとの表示名、組織は gateway の設定の組織名から出します。
IdP の token の `name` などの claim は使いません。
今の gateway は検証した `sub` だけを識別に使い、`email` も存在の確認だけです（[認証と認可](agent-gateway.md#認証と認可分離)）。
IdP によっては、利用者が自分の表示名を変えられます。
token の `sub` は IdP の多要素認証で確かめた値で、運用者がその `sub` に表示名を登録します。
こうして、表示名は IdP で確かめた本人に結びつきます。#404 の「IdP で確かめた名前と組織」は、この意味で満たします。

設定に足す member は、principal の `display_name`（1〜64 文字、制御文字と双方向制御文字を拒否）と、top-level の `organization`（同じ規則）です。
レスキュー用の host に載る principal は `display_name` を必須にします。

### 今の鍵の指紋との対応

身元の証明に、担当者の signer の公開鍵が入ります。
許可したら、その鍵 1 つだけを許可鍵集合にします。channel の handshake は、今と同じく LaunchID を user にした公開鍵認証で、この鍵だけを通します（[認証と照合](agent-channel.md#認証と照合)）。
そのため、ポップアップに出した名前と、実際に接続してくる鍵が結びつきます。
鍵の指紋は、ポップアップの補足に短く出します。

relay（Worker と Cloudflare）は、身元の証明を書き換えられません。
gateway が侵害された場合は守れません。gateway は今も principal の signer を持つ信頼境界です（[信頼の前提](agent-gateway.md#信頼の前提)）。

## 3. 許可と拒否

### ポップアップ

- 主な表示: 「{組織} が確認: {表示名}」。例:「O2 CONNECTIVE が確認: 山田（サポート）」
- 内容: 操作範囲と期限（許可した時刻から選んだ期限まで。時刻で出す）
- 補足: 担当者の鍵の指紋
- ボタン: 「拒否」と「許可」。既定のボタンは置きません。Return では何も起きず、Esc は拒否です。
- 表示から 1 秒間は「許可」を押せなくします。別の操作のクリックが、出た直後のポップアップに当たるのを防ぐためです。

### 誰が判定するか

ポップアップの判定は、ホスト側の Go の許可の状態機械が持ちます。
状態機械が要求 id と、表示する内容の digest を画面に渡します。画面は「要求 id・digest・許可か拒否」を返します。
状態機械は、要求 id と digest が今の要求と一致し、60 秒の内であることを確かめてから grant を発行します。
画面が出した値を認可の根拠にしません（[脅威モデル](threat-model.md#信頼境界と攻撃者)の UI の境界）。
同じユーザーの権限を持つマルウェアが画面を操作する場合は守れません。今の `/dev/tty` の同意と同じ範囲です。

### 60 秒の自動拒否

- ホストの状態機械が、ポップアップを出した時点から、単調時計と壁時計の両方で数えます。どちらかが 60 秒を超えたら拒否です。壁時計が戻ったときも拒否です。
- 画面のタイマーは表示だけです。60 秒を過ぎて届いた「許可」は捨てます。
- gateway は要求から 75 秒（60 秒と通信の余裕 15 秒）で要求を失効させます。その後に届いた許可の回答では channel を開かず、ホストに失効を伝えます。
- 許可の回答が gateway に届かなかったときは、ホストの grant は channel の handshake の期限で失効します（今の fail closed のとおり）。

### 回答

ホストは回答を K で署名して返します。
署名対象は、`rescue-host.agentgateway.rescue-answer\u0000v1\u0000`、受付 id、要求の nonce、身元の証明の digest、回答（`allow`・`deny`・`timeout`）です。
`allow` のときは、grant の dispatch（Binding と期限）も署名対象に入れます。gateway はこれを検証して `Connect` に渡します。
dispatch を真正に届ける責任は登録 adapter にあり（[信頼の前提](agent-gateway.md#信頼の前提)）、この回答の署名がそれを担います。

担当者には、`allow`・`deny`（拒否）・`timeout`（時間切れ）を区別して返します。コードが正しかった場合だけなので、区別しても推測の手がかりになりません。
拒否と時間切れの後、ホストは K を捨てて受付を終えます。次は利用者がもう一度受付を ON にします。

### 担当者の入口

担当者は MCP の新しい tool で、コードを含めて要求します（tool の名前と、待ち方が同期か非同期かは実装で決めます）。
今の MCP は、tool の引数で host や signer を指定させません（[呼出し経路](agent-gateway.md#呼出し経路)）。
この tool は route を選ぶものではなく、ホストに許可を求めるだけです。route は、ホストが許可した後に gateway が作ります。
session を後から grant に束縛しない今の規則は変えません。許可の後、担当者の client は新しい `initialize` で route に束縛します。

1 人の principal が持てる、セッション中か猶予中の受付は 1 つです（live route は 1 principal に 1 本という今の規則と同じ）。
その間の新しい要求は拒否します。再許可待ちの受付は、同じ principal の新しいコードの要求で終わらせます。

## 4. セッションの鍵と猶予

### ホストの状態

| 状態 | 入る条件 | 出る条件 |
| --- | --- | --- |
| 受付中 | 受付 ON。K を作り、コードを出す | 要求が届く → 確認中。コードの失効・受付 OFF → 終了 |
| 確認中 | 身元の証明を検証してポップアップ | 許可 → セッション中。拒否・時間切れ → 終了 |
| セッション中 | grant を発行し、channel が開く | 切断 → 猶予中。期限・ホスト側の切断 → 終了 |
| 猶予中 | channel が切れた | 同じ K で再接続 → セッション中。猶予の超過 → 再許可待ち。期限・ホスト側の切断・回収の未確認 → 終了 |
| 再許可待ち | 猶予を超えた。K を捨て、新しい K2 に引き継ぐ | 同じ担当者の要求 → 確認中（再許可）。期限・ホスト側の切断 → 終了 |
| 終了 | 上のどれか | なし。鍵を捨て、停止と回収に進む |

ホスト側の切断は、利用者の停止の操作、受付 OFF、アプリの終了、OS のログアウトや再起動です。
K はメモリだけにあるので、アプリが終われば K も消えます。
スリープはホスト側の切断ではなく、猶予の時間として数えます。

### 猶予の値

5 分にします。設定では変えません。

- 切断の検出に最大で約 30 秒かかります（心拍 10 秒・応答待ち 10 秒、読取りの停滞 30 秒。[gateway の上限](agent-gateway.md#上限)の channel の予算）。
- Wi-Fi の切り替え、VPN の張り直し、テザリングへの切り替えは、数秒から 1 分ほどです。再接続の間隔を 1・2・4・8・16・30 秒と延ばしても、5 分あれば十分に戻れます。
- 長くするほど、K が漏れたときに許可なしで接続できる時間が延びます。#404 の追加の裁定の理由は、この時間を短くすることです。
- 接続コードの有効時間と同じ 5 分なので、利用者に説明しやすくなります。

### 猶予の数え方

- **ホストの時計で数えます。** 許可と K を持つのはホストです。gateway が侵害されても、ホストは猶予を過ぎた再接続を拒めます。
- 起点は、相手から最後に正しい frame（心拍の応答を含む）を受けた時点です。切断を検出した時点ではありません。検出の遅れの分だけ猶予が延びるのを防ぎます。
- 期限と同じく、単調時計と壁時計の両方で数え、どちらかが 5 分を超えたら超過です（[期限の判定](agent-channel.md)の `WallRecheck` と経過予算と同じ流儀）。壁時計が起点より前に戻ったときも超過として扱います。
- スリープの間は、単調時計が止まることがあります（macOS）。壁時計はスリープ中も進むので、復帰後 1 秒以内に壁時計で超過を見つけます。5 分を超えるスリープの後は、再許可待ちになります。セッション中のスリープは [#400](https://github.com/O2-CONNECTIVE/Tether/issues/400) で防ぎます。
- gateway も、route が終わってから 5 分 30 秒（gateway の単調時計）で、受付記録の猶予を終えます。ホストより先に切らないように 30 秒の余裕を置きます。両者がずれても、ホストの判定が最終です。

### 猶予の間の再接続の確かめ方

猶予の間に再接続できるのは、同じ担当者の、同じセッションの鍵だけです。次の 4 つをすべて確かめます。

1. **ホストから gateway（同じ K）:** ホストは受付口に `resume` で接続し、K で proof を返します。署名対象に受付 id を入れます。gateway は受付記録の K の公開鍵で検証します。K を持たない者は、この受付を名乗れません。
2. **gateway の route（同じ担当者）:** gateway は、受付記録に固定した principal（label と subject）でだけ `Connect` します。route を使えるのは、その principal の token で作った MCP session だけです（今の session の束縛）。
3. **channel の handshake（同じ鍵の組）:** ホストは、許可したときの担当者の signer 1 つだけで公開鍵認証を通します。gateway は host 鍵を K に pin します。commitment に接続世代を入れ、ホストは次の世代以外を拒否します。
4. **ホストの状態:** 猶予中であること（両方の時計）、前の接続の作業の回収を確認済みであること、受付 OFF でないこと。

同じ組織の別の担当者は、2 で gateway が、3 でホストが拒否します。
K を盗んだ者は、担当者の signer を持たないので 3 で拒否されます。
猶予の間の再接続では、ポップアップを出しません。画面に「再接続しました」と出します。

### 接続世代

猶予の間は grant を失効させず、新しい作業の受け付け（admission）だけを止めます。
再接続は、同じ grant の新しい接続世代（1 から増やす）として開きます。

- channel の commitment に世代を入れます。gateway は (LaunchID, 世代) の組を 1 回だけ使います。ホストの Session は、世代ごとに transport を 1 回だけ受け取ります。
- 期限、許可鍵集合、操作範囲、境界は、世代が変わっても変えません。期限は延びません。
- 今の「1 grant に接続 1 回」（[agent channel](agent-channel.md)）を、「1 grant に、世代ごとに接続 1 回」に改めます。ADR 0005 が accepted になってから実装します。

### 猶予の間の作業

切断したら、実行中の作業は今と同じく取り消して回収します。
切断の後も作業を続ける契約の変更は別の issue にする、と #399 で決まっているためです（[PR #413](https://github.com/O2-CONNECTIVE/Tether/pull/413) の「1コマンドのtimeoutの上限240秒は据え置きます」）。
回収を確認できなければ、猶予の間の再接続も拒否し、要清掃のまま終えます（[停止・削除・記録完了は別の結果](temporary-guest-account.md#停止削除記録完了は別の結果)）。
再接続の後は、新しい作業を始められます。

### 猶予の超過と再許可

1. 猶予を超えたら、ホストは grant を失効させ、ゲストの回収に進みます。
2. ホストは新しい K2 を作り、K で「K2 への引き継ぎ」に署名してから K を捨てます。引き継ぎの署名対象は、`rescue-host.agentgateway.rescue-rekey\u0000v1\u0000`、受付 id、K2 の SSH wire 形式です。オフラインでも作れます。
3. ホストは gateway に戻れたら、受付口に `rekey` で接続し、引き継ぎと K2 の proof を送ります。gateway は受付記録の K で引き継ぎを検証し、K2 に差し替えます。以後、K では何もできません。
4. 受付記録は再許可待ちになります。要求できるのは、受付記録に固定した principal だけです。コードは要りません。
5. 担当者が同じ tool でコードなしに要求すると、gateway は種類 `reapproval` の身元の証明を送ります。ホストはポップアップ（再接続の許可）を出します。60 秒の自動拒否も同じです。
6. 許可したら、K2 で新しい grant を発行します。期限は最初の許可のまま延ばしません（延長はホスト側の操作だけ。#399）。ゲストのアカウントは新しく作ります。
7. 拒否と時間切れでは、K2 を捨てて受付を終えます。

ホストが期限まで戻らなければ、gateway は期限で受付記録を消します。K はホストが捨てているので、誰も使えません。
担当者を替えるときは、利用者がもう一度受付を ON にして、新しいコードを伝えます。

### 期限とホスト側の切断

猶予に関わらず、grant を失効させ、K（再許可待ちなら K2）を捨て、停止と回収に進みます。
ホストは gateway に接続していれば受付の終了を伝えます。接続していなければ、gateway は期限で受付記録を消します。

### ゲストのアカウントとの対応

| 事象 | grant | 鍵 | ゲストのアカウント | 作業 |
| --- | --- | --- | --- | --- |
| 許可 | 発行 | K を保持 | 作成（[作成と有効化の境界](temporary-guest-account.md#作成と有効化の境界)） | 受け付ける |
| 切断（猶予に入る） | 失効させない。admission を止める | K を保持 | 保持する（無効化しない） | 取り消して回収 |
| 猶予の間の再接続 | 同じ grant の次の世代 | 同じ K | 同じアカウント | 受け付ける |
| 猶予の超過 | 失効 | K を捨て、K2 に引き継ぐ | 停止の手順で無効化・回収・削除 | 回収済み |
| 再許可 | 新しい grant | K2 | 新しく作る | 受け付ける |
| 期限・ホスト側の切断・拒否 | 失効 | 捨てる | 停止の手順で無効化・回収・削除 | 回収 |

猶予の間にアカウントを無効化しないのは、作業の起動を Tether の supervisor が持ち、admission を止めればゲストの新しいプロセスが始まらないからです。
再有効化の前の再検査を、猶予のたびに増やさずに済みます。

今の Mac の入口は、現在ユーザーの権限で隔離なしに動きます（[Mac runtime](mac-agent-runtime.md)）。
[一時guestアカウント](temporary-guest-account.md) の設計は Windows の API で書かれていて、Mac のゲストのアカウントは未設計です。
この流れを製品として有効にするのは、そのホストの OS でゲストのアカウントを使えるようになってからです。
それまでは、Go の側の受付・コード・身元の証明・許可の状態機械を、今の境界（現在ユーザー・隔離なし）で試験だけに使います。ポップアップには、今の承認画面と同じく隔離なしの警告を出します。

## 5. 今のパイロットの置き換え

| 今（[人間側の実装済み入口](tether-pilot-status.md#人間側の実装済み入口)） | この流れ |
| --- | --- |
| 受け手が `rescue-mac-agent -config` を前景で起動する。保護設定に gateway の principal の pin と既登録の host 鍵がある | 受付 ON で K を作る。アカウントも既登録の鍵も無い。pin するのはアプリに同梱した身元の証明鍵だけ |
| 承認画面に Host と全 Client 鍵の SHA256 指紋、失効時刻、作業フォルダ、HOME、隔離なしの警告を出す | ポップアップに組織と表示名を主に出し、操作範囲と期限、補足に担当者の鍵の指紋を出す |
| 確認文字列 `approve <LaunchID の SHA-256 の先頭 8 byte の hex>` を `/dev/tty` に打ち込む | 既定ボタンの無い「許可」、表示から 1 秒の無効化、60 秒の自動拒否 |
| 許可鍵集合は設定の Client 鍵 | 許可鍵集合は身元の証明の担当者の signer 1 つ |
| 期限は設定の絶対時刻（上限 24 時間） | 期限は許可の時刻から、選んだ 2・4・8・12・24 時間（既定 2 時間） |
| 1 grant に接続 1 回、再接続なし | 猶予 5 分の間だけ、同じ grant の次の世代で再接続 |

確認文字列が守っていたのは、本人がその場で画面を見て同意したことと、引数や pipe で同意を渡せないことです。
この流れでは、既定ボタンを置かないこと、表示直後の無効化、60 秒の自動拒否、画面の値を認可の根拠にしない状態機械で守ります。

今の経路（`rescue-mac-agent -config`、確認文字列、旧の `Connect`）は、この流れの Go の側が入るまで残します。
この流れが入ったら、レスキューは今の承認画面と確認文字列を使いません。今の経路を消すかどうかは、実装の issue で決めます。
[検証状態](tether-pilot-status.md)の固定証跡は履歴として残し、この流れの成功に読み替えません。

## 試験で確かめること

#409 の受け入れ条件と、追加の裁定の分です。実装の issue で red から書きます。

| 確かめること | 試験の形 |
| --- | --- |
| 受付 OFF のホストに要求が届かない | 受付 OFF の後のコードの照合が「コードが無効」になり、ホストに要求が届かない。ホストは受付 OFF のときに届いた要求でポップアップを出さない |
| コードは 1 回だけで、失効後は使えない | 2 回目の照合が無効。5 分を過ぎたコードが無効。拒否・時間切れの後のコードが無効 |
| `rescue_operator` の無い principal は要求できない | `resident_owner` だけの principal の要求が、コードの照合の前に拒否される（失敗の回数にも数えない） |
| 拒否と 60 秒の自動拒否で接続が始まらない | 拒否・時間切れで grant が発行されず、`Connect` が呼ばれない。60 秒を過ぎた許可の回答を捨てる。75 秒を過ぎた回答で gateway が channel を開かない |
| 期限と切断で鍵が捨てられ、同じ鍵で再接続できない | 期限・ホスト側の切断・猶予の超過の後、K での `resume` と、旧 grant の Binding での channel が拒否される |
| 猶予の間は同じ担当者・同じ鍵で再接続できる | 5 分以内の `resume` で次の世代の channel が開く。別の principal・別の signer・同じ世代の再利用は拒否される |
| 猶予の数え方 | 単調時計だけが進む場合・壁時計だけが進む場合（スリープの模擬）・壁時計が戻る場合のそれぞれで、5 分を超えたら再許可待ちになる |
| 回数の制限 | 失敗 5 回で principal が 10 分止まり、ほかの principal は止まらない。有効なコードが 100 件で新しい受付が 503 になる |
| 身元の証明 | 署名・受付 id・K・要求の種類のどれかが違えばポップアップを出さない。表示名と組織が設定から来る |

## 脅威と残るリスク

| 脅威 | 守り | 残るもの |
| --- | --- | --- |
| コードの推測 | 12 桁、5 分、1 回限り、照合は `rescue_operator` だけ、principal ごとの失敗の上限 | 1 年で 1.1 × 10^-4 以下の確率。当たってもポップアップで拒否できる |
| 匿名の受付で枠を埋める | 有効なコードの上限、全体と IP ごとの登録の速度 | 多数の IP からの攻撃では、正規の利用者が受付を ON にできないことがある（可用性） |
| 利用者からコードを聞き出す | 照合できるのは `rescue_operator` だけ。ポップアップに名前と組織が出る | 内部の担当者による悪用。監査の記録で追う |
| 偽のホストのコードを担当者に渡す | 担当者がコードを利用者本人から受け取る運用 | 担当者が偽のホストに作業を送ること。担当者の側の情報が漏れうる |
| relay が身元を書き換える | 身元の証明の署名、channel の鍵の pin | なし（gateway の侵害は別） |
| K の漏れ | K はメモリのみ。猶予の間しか許可なしで使えない。猶予の超過で捨てる | ホストの侵害（範囲外） |
| ポップアップの誤操作 | 既定ボタンなし、1 秒の無効化、60 秒 | 利用者が読まずに許可すること |
| ポップアップの連発 | コードは 1 回限りで、1 コードにポップアップ 1 回。再許可も拒否で終わる | なし |
| gateway の侵害 | 範囲外。今も principal の signer を持つ信頼境界 | 身元の偽装と接続 |
| gateway の再起動 | 状態はメモリのみ。受付記録が消え、ホストの `resume` は失敗し、猶予は終わる | 再起動の直後の再接続ができない（安全側） |

## 範囲外と後続

- ポップアップと受付の画面（[#410](https://github.com/O2-CONNECTIVE/Tether/issues/410)）。
- Mac のゲストのアカウントの実体（作成・削除・権限の確認）。Windows は [ADR 0003](adr/0003-owned-guest-workload.md) と [一時guestアカウント](temporary-guest-account.md) の経路です。
- 猶予の間も作業を続けること。#399 で別の issue にすると決まっています。
- 担当者の交代と、1 人の担当者が同時に複数のホストを助けること。
- 担当者の多要素認証の強制（[#398](https://github.com/O2-CONNECTIVE/Tether/issues/398)）。#415 の `role_assurance` の `multi_factor` は #398 が入るまで指定できません。製品として有効にする前提です。
- 身元の証明鍵の配布と差し替えの手順（配布の issue）。
- 受付口の wire の正確な形（frame、subprotocol 名、tool の名前と待ち方）。実装の issue で、この文書の署名対象と不変条件を守って決めます。
