# 安全要件と接続停止の理由

> **対象範囲の更新（2026-11-01）:** 以下の旧SSH / Windows / Pythonに関する本文・受入条件は、その方式と記録時点の履歴として保持しています。現在のTetherはAI commandと一時派遣を目標にMacを優先し、現状の正本は[文書索引](README.md)と[検証状態](tether-pilot-status.md)です。旧ゲート閉鎖や未達を解除・達成扱いにはしません。Macは現在ユーザー・非sandboxであり、Windows隔離guestの保証を引き継ぎません。

[READMEへ戻る](../README.md)

**v0.2.1-devは新規接続を停止しており、本番利用できません。**
既存UptermではTCP転送先を`127.0.0.1:22`だけに強制できず、同一ユーザー権限の監視プロセスでは確実な失効も保証できません。
GUIと起動ワーカーの両方で開始を拒否し、設定や環境変数から解除するスイッチはありません。

## 保証できない境界

- Uptermの公開鍵認証は、OS上の最小権限化ではありません。
  旧SSH転送モードはPowerShellも起動するため、内側sshd認証だけを頼りにできません。
- OpenSSHの`authorized_keys`の`permitopen`などをUptermに渡しても、その制約は強制されません。
- オフラインモデルはSSHサーバー、実認証、Windowsサービス、OS権限分離、独立したタイマーを提供しません。
  呼び出し側の定期確認停止やPythonのハング、終了処理の無応答まで失効を保証しません。
- GUI終了や鍵ファイルの削除は、既存接続の終了証明ではありません。
  通信を終了しても、実行済み変更、切り離されたプロセス、取得された認証情報は取り消せません。

旧セッションは更新後も安全になりません。
[回復時のリスクと記録の扱い](recovery.md)を確認してください。

## 接続を再開する前の条件

実SSHのチャネル制約、固定宛先の強制、ゲストから保護されたWindows監督、内側sshdとヘルパーの権限制御、実接続と故障注入の検証が必要です。
モック試験の合格や利用者の承認だけで開始ゲートを解除しません。
詳細な受け入れ条件は既存の[バックエンド契約](SECURITY_BACKEND_CONTRACT.md)に集約しています。

認証helperの[採用範囲](adr/0004-localservice-auth-helper.md)に対応する受入では、非管理者guestによる認証偽造と監督・停止処理への干渉を対象にします。
侵害済みの別Windows serviceからの完全防御は保証しませんが、専用SID、固定配置、実process/token、object owner/DACLの一致と、失効・停止回収の条件は維持します。
processの照会許可だけでtokenの複製・偽装を許すことにはならず、token objectのDACLを独立に確認します。照会と停止・改変を同じ権利として扱いません。
source/fake試験は検査と拒否・所有保持の確認、Windows compileはAPI宣言の確認です。実機の設定適合、実message認証、期限停止・撤去は別に実証します。
この範囲明記によって既存44条件や未検証の合否を変更せず、実機操作の承認とも扱いません。
